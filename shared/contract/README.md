# The shared contract

This directory is the normative description of everything the JavaScript and
Python packages must agree on. Both packages describe one dataset; two packages
over one dataset that disagree about record identity, or about what a search
returns, are worse than either package alone, because a consumer joining them on
`id` gets silent mismatches rather than an error.

## How the contract is enforced

Prose alone does not hold two implementations together — the rules below were
written down once before and both were still reimplemented by hand, which is how
a slug rule loses a step. So the contract has three layers, and only the first
is human-readable:

| Layer | What it is | What it catches |
|---|---|---|
| `shared/contract/*.md` | the rules, and **why** each one is the way it is | a reader reimplementing from a misunderstanding |
| `shared/fixtures/*.json` | generated by `scripts/build-data.ts`, read by **both** test suites | a divergence, in either language, on any covered input |
| `tests/shared-fixtures.test.ts` | asserts the fixtures describe the real shipped API | a fixture hand-edited to make a test pass |

The fixtures are ordinary build outputs. `pnpm build:data --check` regenerates
them and fails if a byte differs, and the orphan sweep fails on a stale file, so
a behaviour change that is not reflected in the fixtures cannot be committed.

**Never hand-edit `shared/fixtures/`.** Change the implementation, run
`pnpm build:data`, and review the fixture diff — that diff *is* the change to
the cross-language contract, which is exactly what should be under review.

## What is deliberately NOT shared

Executable code. There is no transpilation step and no generated Python, by
decision **PY-D2**: the reason the JavaScript package inlines its data as
TypeScript constants is that `node:fs` breaks browsers, bundlers, Workers and
Deno. Python has no equivalent constraint — no bundle size, no browser target,
no tree-shaking — so it reads the same `data/*.json` the jq and CDN consumers
read, and a 1541-record `.py` literal would be slow to byte-compile and heavy in
memory for no benefit.

So the two implementations are independent by design, and the fixtures are what
keep them honest.

## Language notes

Both implementations must produce identical output, and the two runtimes differ
in ways that are easy to miss. These are the ones that actually bite on this
corpus, or would if the data changed:

- **`\s` is not the same set.** JavaScript's includes `U+FEFF` and excludes
  `U+001C`–`U+001F`; Python's `re` does the reverse. Neither `String.trim()` nor
  `str.strip()` trims the same set either. Use an explicit character class.
- **`\d` is Unicode-aware in Python.** `re.match(r"\d{5}", "١٦٠٠٠")` succeeds,
  and so does `"١٦٠٠٠".isdigit()`. Postal-code validation must use `[0-9]` or
  `re.ASCII`, or Arabic-Indic digits pass.
- **String comparison.** JavaScript `<` compares UTF-16 code units, Python
  compares code points. They agree on this corpus, which is entirely within the
  BMP, but the build-time sort and the runtime binary search must use the same
  rule or every prefix lookup silently misses.
- **`length`.** JavaScript counts UTF-16 code units, Python counts code points.
  The score formulas and the Levenshtein length prefilter both divide by it.
  Equivalent here; not equivalent if an astral character ever enters the data.
- **`toLowerCase()` vs `str.lower()`** differ on a handful of code points
  (Turkish dotted I, Cherokee, sharp S). None occur in this dataset.

`bool` is an `int` subclass in Python, so a wilaya-code guard that only checks
`isinstance(n, int)` accepts `True`. JavaScript has no equivalent trap.
